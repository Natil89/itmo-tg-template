# Лабораторная 2: спецификация

Актуальное расширение лабораторной 3 приведено в конце документа. Разделы ЛР2
ниже сохраняют историю требований; более поздние явно описанные изменения имеют приоритет.

Текущий этап: расписание через настоящий MCP, команда `/tools` и выбор
`get_schedule` моделью по естественному вопросу. Функции лабораторной 1 сохраняются.

## Контракты

- R1: `get_schedule({date: "YYYY-MM-DD"})` возвращает `{date, lessons}`.
  Занятие содержит `start`, `end` (HH:MM), `title`, `location`.
  Отсутствие занятий — пустой список; неверная дата и лишние поля — ошибка.
- R2: ресурс `schedule://current-week` возвращает `{timezone, start, end, days}`:
  семь дат с понедельника по воскресенье в настроенной IANA-зоне, включая пустые дни.
- R3: `/tools` показывает обнаруженные через MCP имена, описания и тип операции.
  При недоступности сервера сообщает об этом; обычный диалог остаётся доступен.
- R4: источник расписания задаётся только конфигурацией; модель не передаёт пути.
  Демонстрационный файл содержит две недели вымышленных занятий.
- R5: входные и выходные схемы публикуются сервером; результат инструмента
  находится в `structuredContent`. Соединение и дочерний процесс закрываются при остановке.
- R6: запуск MCP ожидается до 60 секунд, обычный запрос ограничен десятью секундами.
  Диагностика содержит этап и типы вложенных ошибок без их текста и секретов.
- R7: модель получает обнаруженную схему расписания и доверенное текущее время.
  По вопросу «Какие занятия завтра?» предлагает дату, приложение проверяет имя,
  аргументы и результат. Результат возвращается как tool message; максимум два
  MCP-вызова на сообщение. Неоднозначная дата требует уточнения.
- R8: необязательный служебный `tool_calls[].index` провайдера допускается только
  как неотрицательное целое число (или null) и исключается из следующего запроса.
  Неизвестные поля вызова и лишние аргументы инструмента по-прежнему запрещены.

## Следующие этапы полной лабораторной

- `get_weather({city})`: нормализованный город/страна, температура C, условия,
  ветер с единицей, время и зона наблюдения; неоднозначный город требует уточнения.
- `add_reminder({text, remind_at})`: только после подтверждения; будущий ISO-момент
  с зоной, текст 1–500 символов. Владелец и ключ повторов поступают от приложения.
  Результат: идентификатор, время, зона, признак создания новой записи.
- Подтверждение в PostgreSQL: pending → executed / cancelled / expired,
  срок не больше пяти минут; повторный update и конкурентное подтверждение не дублируют запись.
- Расширение агентного цикла на погоду и подтверждённые напоминания.
- `/timezone`, `/why`, аудит, интеграционные тесты PostgreSQL, эксперимент 12 запросов.

Это первоначальный план; актуальный статус приведён в следующих разделах и plan.md.

## Расширение: погода и личное расписание (16.11.2026)

- W1: get_weather({city}) читает текущую погоду Open-Meteo. Фиксированные HTTPS
  endpoints, город 1–100 символов, конечные тайм-ауты и ограниченные повторы GET.
  Результат status=ok/not_found/ambiguous; ok содержит город, страну, температуру C,
  код условий, ветер m/s, момент и IANA-зону. ambiguous содержит варианты со страной
  и областью; бот уточняет выбор, не выбирает первый автоматически.
  Если API не прислал название страны, используется его двухбуквенный ASCII-код;
  отсутствие названия у одного варианта не должно превращать весь ответ в ошибку.
  Точное нормализованное имя имеет приоритет перед префиксными совпадениями:
  Ереван не смешивается с Еревани/Ереванлы. Если точных имён несколько, требуется
  выбор; население сортирует варианты, но не даёт права выбирать автоматически.
  При отсутствии точного совпадения похожие варианты сохраняются для уточнения.
  По последующему выбору пользователя для обычного запуска добавлен режим population:
  среди нескольких точных совпадений с единственным известным лидером по населению
  погода запрашивается сразу, но место явно обозначается как предположение и
  предлагается уточнить страну/регион. Если положительных данных нет или у лидеров
  равенство населения — уточнение. Отсутствующее значение не даёт приоритета;
  выбор по одному известному положительному значению остаётся явным предположением.
  WEATHER_LOCATION_POLICY=strict сохраняет исходное обязательное поведение методички;
  population — намеренное пользовательское отступление, не доказательство сдачи критерия.
- P1: в работающем боте get_schedule читает PostgreSQL только для владельца из
  Telegram. Новые пользователи получают пустое расписание. Общий JSON остаётся
  обезличенным демонстрационным источником standalone-сервера, не смешивается с
  личными данными. Отдельная БД для каждого пользователя не создаётся.
- P2: add_lesson({date,start,end,title,location}) предлагается моделью по обычному
  сообщению. Все поля обязательны; неизвестные сведения бот уточняет. Переход
  prepared → confirmed → executed требует явного нажатия пользователя. Подтверждение
  живёт не более пяти минут, отмена/просрочка запрещает выполнение.
- P3: владелец и идентификатор подготовленного действия не входят в tool arguments.
  Клиент передаёт подписанный доверенный контекст через MCP _meta; сервер проверяет
  подпись, время, инструмент и аргументы, а для записи — подтверждённое действие БД.
  Чужое действие нельзя прочитать, подтвердить или выполнить.
- P4: повтор подготовки одного Telegram-сообщения и конкурентное подтверждение
  создают одну подготовленную операцию и одно занятие. PostgreSQL-тест обязателен.
- P5: ресурс current-week в личном режиме также изолирован по владельцу. Discovery
  не раскрывает содержимое расписаний. Погода общедоступна, владельца не требует.

Решение пользователя: личное расписание — дополнительная возможность к лабораторной;
добавление свободным текстом с подтверждением. Напоминания реализованы отдельным этапом ниже.

## Напоминания и пользовательская зона (16.11.2026)

- N1: `/timezone <IANA>` сохраняет зону владельца Telegram update, показывает местное
  время; без аргумента показывает сохранённую зону или подсказку настройки.
  Дополнение 17.11.2026: аргументом может быть город (включая страну/регион после
  запятой). TimezoneResolver проверяет IANA либо обращается к фиксированному
  Open-Meteo Geocoding. В БД передаётся только проверенная ZoneInfo-зона. Приоритет
  точного имени; одинаковые зоны не требуют выбора. Для разных зон допустим явный
  лидер с населением >=10 ближайшего конкурента либо большой город >=100000 при
  неизвестном населении остальных. Выбор явно назван; иначе нужно уточнение.
  Ошибка/неоднозначность поиска не изменяет прежнюю настройку.
- N2: модель предлагает только `add_reminder({text, remind_at})`; text 1–500 символов,
  remind_at ISO 8601 с offset. Отсутствующая сохранённая зона программно блокирует
  подготовку. Относительные даты вычисляются по личной зоне.
- N3: prepare нормализует время, проверяет будущее, соответствие offset IANA-зоне и
  отсутствие DST gap/fold. После ответа LLM используются свежие рабочие часы.
- N4: TTL не более пяти минут; owner и действие из доверенного контекста, неизменные
  текст/момент/зона. Только callback переводит подготовленное действие в confirmed,
  только MCP выполняет атомарную запись и перевод в executed.
- N5: owner-filtered SQL, UNIQUE(user_id, update_id), UNIQUE(action_id), row locks и
  composite owner FK предотвращают чужую запись и конкурентные дубли. Проверки TTL
  и будущего выполняются после блокировки; выполненный повтор возвращает created=false.
- N6: результат содержит reminder_id, текст, момент, IANA-зону и created. Обработчик
  проверяет результат до сообщения об успехе. Отправка по времени ещё не реализована.

Эксперимент 12 запросов выполнен (раздел ниже); следующий этап — оформление сдачи.

## /why и аудит (17.11.2026)

- A1: /why читает только последнюю запись владельца из доверенного Telegram update.
  Сама команда не пишет новое событие, не меняет диалог и не вызывает модель/MCP.
- A2: PostgreSQL хранит время, длительность и ограниченный список этапов: действие,
  whitelisted инструмент/аргументы, проверка, выполнение, фиксированная причина.
  Уникальный ключ (user_id, request_key) защищает повторную запись одного события.
- A3: Не сохраняются промпт, история, raw tool args, тексты напоминаний/занятий,
  неизвестные поля и имена инструментов. Внутренние owner/action/request IDs не
  выводятся. Из безопасных строк удаляются известные секреты приложения и прокси.
- A4: Отдельные этапы отражают batch validation, два независимых чтения, отказ,
  лимит двух MCP-вызовов, ожидание/подтверждение/отмену и ошибку после успешного чтения.
- A5: Для ответа без tool calls дополнительный JSON-классификатор различает respond
  и clarify. Это только диагностика публичного ответа, не выбор полномочий; максимум
  10 секунд, при сбое action=undetermined и исходный ответ сохраняется.
- A6: Сбой аудита не вызывает повтор бизнес-действия и не скрывает его успех.
  /why показывает безопасную ошибку недоступности; обычный ответ при сбое записи
  дополняется предупреждением. /reset очищает историю, но не аудит.

## Лабораторная 3: текущий этап (23.11.2026)

- L3-R1: AssistantService сохраняет translate/quiz без MCP. В study Router выбирает
  одного специалиста либо уточнение. Обычный диалог отмечается `dialogue=true`
  при `target=clarify` и тоже выполняется без инструментов. Уверенность <0.6,
  неизвестная цель и противоречивые поля не запускают специалиста.
- L3-R2: ScheduleSpecialist, KnowledgeAgent и LifestyleAgent имеют разные инструкции,
  контекст и точные программные права (constitution.md). Supervisor проверяет
  идентификаторы, статус, факты и used_tools по свидетельствам ScopedMcp.
  `operation=read|prepare_reminder|prepare_lesson` уточняет задачу, не расширяя прав.
- L3-R3: Knowledge читает обнаруженный materials://catalog, ищет через search_materials
  и передаёт каталог/фрагменты в контекст. Источники добавляет приложение. Пустая
  выдача даёт честный not_found без генерации ответа из памяти модели.
- L3-R4: Lifestyle получает текущую погоду и дополняет совет проверенными значениями,
  временем и источником. Профиль population сохраняет пометку предположения и
  предложение уточнить место; рабочая настройка не меняется.
- L3-R5: Schedule читает дату и текущую неделю; другие недели не подменяются текущей.
  add_reminder подготавливает карточку через ReminderStore, а не исполняет MCP.
  add_lesson выделен в LessonCompatibility: проверка запроса, извлечение черновика,
  prepare; до согласия запись занятия не выполняется. Старый универсальный агент
  больше не используется в основном пути приложения.
- L3-R6: уточняющие ответы используют до четырёх последних user/assistant сообщений
  по 4000 символов. История — данные, не источник owner/time/прав. Фоновый intent
  не принимает историю. Нормализованные ISO-моменты сравниваются как datetime.
  После вопроса о городе короткий ответ с названием города может восстановить
  маршрут чтения погоды, если Router не определил специалиста уверенно. Запросы
  прогноза вроде «Какая завтра погода?» получают сообщение о поддержке только
  текущих условий, в том числе при продолжении такого запроса названием города.
- C1: по позднему указанию пользователя занятие подтверждается кнопкой или точными
  фразами «да», «всё верно», «подтверждаю». «Да, но поменяй время» — не согласие.
- C2: текст относится только к реально отправленной карточке текущего владельца,
  по сохранённым chat_id/message_id, в пределах пяти минут. При нескольких карточках
  требуется reply на нужную. В translate/quiz текстовое согласие всегда требует reply.
- C3: кнопка и текст используют общий confirm_lesson с повторной проверкой discovery,
  политики lesson_compat и схемы перед исполнением. Сохраняются owner isolation,
  неизменность параметров и PostgreSQL-защита от конкурентных дублей. Это изменение
  прежнего P2 о нажатии кнопки; напоминания пока подтверждаются только callback.

Оставшиеся требования ЛР3 перечислены в plan.md; завершение всей работы не заявляется.

## Доставка напоминаний (23.11.2026)

- D1: исполнитель не вызывает LLM. Для подтверждённого напоминания DeliveryStore
  создаёт постоянное событие `reminder:<id>` до отправки. UNIQUE(event_id/reminder_id),
  FK владельца и ON CONFLICT защищают повторную/конкурентную подготовку.
- D2: адрес хранится отдельно в delivery_destinations и берётся middleware только
  из доверенного update личного чата. Модель/MCP/документ адрес не задают.
  Перед отправкой проверяются владелец, адрес, событие, текст, срок и аренда.
- D3: pending → sending → sent либо retry/failed/missed переживают перезапуск.
  Захват атомарный, FOR UPDATE SKIP LOCKED; lease 60 секунд при таймауте отправки
  10 секунд. Свежие часы проверяются и после ожидания БД.
- D4: напоминания отправляются отдельно. При 0 < задержка <= 15 минут добавляется
  пометка. Более старые получают missed без отправки; будущие ожидают.
- D5: максимум три попытки всего. Повторы после временной ошибки: 30 и 120 секунд,
  с учётом большего Telegram retry_after и 15-минутного окна. Постоянная ошибка
  завершает обработку. Прерванная попытка расходует слот; после lease задание можно
  взять повторно. Диагностика содержит безопасный код, не текст сообщения/ошибки.
- D6: REMINDER_DELIVERY_ENABLED=false по умолчанию. Включение — явное изменение
  конфигурации и перезапуск одного процесса. При отключении нет фоновой отправки
  и сбора новых адресов. Ответы показывают, включена ли автоматическая доставка.
- D7: exactly-once не обещается: сбой после отправки до фиксации sent может привести
  к дублю. Уникальность задания этот остаточный риск не устраняет.

Сводка, проактивный профиль и трассировка описаны в следующих разделах.

## Подтверждённый город и ежедневная сводка

- B1: /city выполняет геокодирование по фиксированному Open-Meteo endpoint.
  Показываются нормализованные город, страна и регион, варианты не выбираются
  автоматически даже при погодном профиле population. Координаты до согласия —
  только в RAM. Право подтверждения действует пять минут; очистка RAM каждые
  15 секунд и при обращении к истёкшему предложению. После рестарта неподтверждённый
  выбор нужно повторить. Подтверждённые настройки остаются в PostgreSQL.
- B2: callback связан с owner/chat/token; повторный token не меняет выбранный город
  и не отзывает позднее согласие на сводку. TTL перепроверяется после ожидания
  блокировок БД перед записью координат. Выбор нового города выключает сводку.
- B3: /briefing_on — отдельное согласие, только после подтверждения города и настройки
  timezone. /briefing_off отзывает согласие, включая ещё не отправленные задания.
  /notifications показывает место/зону/статусы без IDs и координат. Настройка города
  не заменяет /timezone и не включает сводку сама по себе.
- B4: BriefingStore сохраняет событие `briefing:<actor>:<local-date>` до подготовки,
  UNIQUE(actor_id,local_date) защищает последовательные/конкурентные запуски.
  В 08:00 локального дня допускается подготовка/доставка до 60 минут включительно.
  Будущее не запускается; после окна новый запуск пропускается до следующего дня.
- B5: чтение четырёх разделов параллельное, по одному обращению к каждому компоненту
  с таймаутом пять секунд. Пустые данные и ошибки/таймауты различаются. Доступные
  разделы отправляются с причинами пропусков остальных, временем подготовки и зоной.
  Погода запрашивается по подтверждённым координатам без нового геокодирования.
- B6: учебный фокус — совет повторить тему найденного документа со ссылкой. Материал
  выбирается детерминированной ротацией по локальной дате, затем ищется в корпусе.
  Для небольшого локального корпуса отдельный кэш не нужен; готовый текст сводки
  сохраняется в исходящем задании и не генерируется заново при повторах отправки.
- B7: перед отправкой повторно проверяются согласие, версия профиля, timezone,
  получатель, дата/время, lease и тело задания. После ожидания БД проверяются свежие
  часы. При смене города, зоны или адреса старая сводка не отправляется.
- B8: состояния и три попытки переживают рестарт; lease 60 секунд, send timeout 10,
  интервалы 30/120 секунд с учётом retry_after и часового окна. Exactly-once нет:
  после фактической отправки без записи результата остаётся риск дубля.
- B9: сводка управляется согласием /briefing_on/off независимо от переключателя
  автодоставки напоминаний. Источники работают только на чтение через репозитории,
  WeatherService и MaterialsService; LLM/MCP-записи в фоне не вызываются. История
  диалога и инструкции из документов в управление фоновым заданием не попадают.

Следующий раздел описывает трассировку. План эксперимента, проверки безопасности
и оформления сдачи приведён в plan.md.

## Трассировка

- T1. PostgreSQL хранит трассу владельца и этапы с общим `trace_id` и `request_id`.
  Каждый этап имеет собственный `span_id` и при наличии родителя `parent_span_id`.
  Сохраняются начало, конец, длительность, компонент, операция, статус и безопасный код.
- T2. Обычный запрос связывает Telegram, Router, выбранного специалиста, LLM,
  фактические вызовы/чтения MCP и ответ. Фоновые трассы создаются на захваченные
  попытки доставки. Для сводки отдельно видны чтения разделов и отправка.
- T3. Числа входных и выходных токенов берутся только из `usage` ответа провайдера.
  Необязательные значения хранятся как SQL NULL. Промпты, тексты, аргументы,
  ответы, причины модели и произвольные ошибки не сохраняются.
- T4. `/trace last` показывает последнюю сохранённую трассу владельца.
  `/trace <id>` фильтрует по владельцу и ID в одном запросе. Для чужой и отсутствующей
  трассы ответ одинаковый. Просмотр сам не создаёт трассу.
- T5. Трасса и этапы сохраняются одной транзакцией при завершении операции.
  Сбой записи диагностики не повторяет бизнес-действие. Если процесс аварийно
  завершится посреди операции, незаписанная трасса может потеряться.

Проверки T1–T5: `tests/test_tracing.py`, `tests/test_tracing_integration.py`.
Полный прогон в WSL с `RUN_INTEGRATION=1` и отключённым кэшем pytest дал
654 успешных теста. Он включал отдельную PostgreSQL, фиктивный Telegram
и повторную проверку чтения MCP и подготовки занятия после исправления таймаутов.
