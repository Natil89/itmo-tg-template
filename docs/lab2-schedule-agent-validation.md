# Подключение MCP в WSL и вопросы к расписанию

Дата: 15 ноября 2026 года. Это продолжение первого этапа лабораторной 2;
погода, напоминания, аудит `/why` и эксперимент маршрутизации ещё не выполнены.

## Что изменилось

- R6: собственный MCP-сервер получает отдельные 60 секунд на инициализацию.
  Рабочие discovery-запросы и вызовы агента ограничены десятью секундами.
  Лог показывает этап, безопасные типы вложенных ошибок и числовой MCP-код.
- R7: ScheduleAgent получает обнаруженную схему get_schedule и доверенные часы
  в зоне SCHEDULE_TIMEZONE. Native tool_calls проходят проверку имени, JSON,
  схемы, календарной даты и всего batch перед выполнением. Лимит — два вызова.
  Результат проверяется по outputSchema и передаётся как role=tool с источником.
- Обработчик сохраняет только финальную пару user/assistant в прежнюю историю.
  Старые пары истории сокращаются по общей оценке размера; текущий вопрос,
  системные инструкции, примеры и tool-обмен не удаляются.

Сервис расписания по-прежнему не зависит от Telegram. MCP-клиент отвечает за
процесс и соединение; агент — за проверку предложенных моделью действий;
LLM-клиент — за HTTP и проверку структуры ответа. Новых таблиц БД нет.

## Воспроизведение и целевые проверки

Старый клиент в существующей WSL .venv воспроизвёл отказ: connected=False,
12,39 секунды с учётом закрытия процесса. Текст ExceptionGroup не показывал
вложенную причину. После изменения лимита и окружения процесса реальное
подключение успешно: tools=1, resources=1, startup_seconds=10.98. Медленный
старт, выходящий за прежние десять секунд, теперь покрыт отдельным тестом.

- WSL: `.venv/bin/python -m pytest -q tests/test_schedule_mcp.py
  --basetemp=.pytest-tmp-wsl-mcp` — 22 passed, 126,47 секунды.
  Затем добавлен дополнительный тест закрытия транспорта при startup timeout.
- Windows: `.venv-windows/Scripts/python.exe -m pytest -q
  tests/test_assistant.py tests/test_lifecycle.py tests/test_schedule_mcp.py
  --basetemp=.pytest-tmp-connection-fix` — 65 passed, 45,25 секунды.
- Ruff check, format --check, git diff --check — PASS.
- WSL: `.venv/bin/python -m pip check` — **No broken requirements found**.
- Итоговый WSL: `.venv/bin/python -m pytest -q
  --basetemp=.pytest-tmp-wsl-acceptance -rs` — **212 passed, 2 skipped**,
  125,01 секунды. Пропущены только два Docker/PostgreSQL integration-теста:
  специальный флаг RUN_INTEGRATION не включался.

Независимая приёмка текущего этапа пройдена после полного прогона тестов.
Ревью выявило и проверило исправление несовпадающих оценок контекста.
Регрессионные тесты проверяют границу бюджета и рост tool-ответа; сквозной тест
соединяет агента с настоящим MCP-сервером и строит ответ из реального занятия.

## Ограничения проверки

Модель подменяется контролируемыми ответами, Telegram — тестовыми объектами.
В основном автоматическом прогоне реальные LLM/Telegram API не вызывались, работающий бот
не останавливался и не перезапускался. Тесты доказывают программные границы,
но не качество маршрутизации живой модели и не абсолютную стойкость к prompt injection.
На этом этапе живую модель ещё не проверяли. Последующая проверка описана ниже;
обязательный эксперимент на 12 запросах пока не выполнен.

## Исправление служебного index в ответе провайдера

После пользовательской проверки выявлено несоответствие реального ответа тестовой
фикстуре: провайдер возвращал `tool_calls[].index=0`. Поля вызова и аргументы были
правильными, но прежняя Pydantic-модель отклоняла индекс как лишний атрибут.
R8: теперь индекс допускается как необязательное неотрицательное целое (или null)
и исключается из нормализованного assistant-сообщения. Неизвестные атрибуты,
неверные типы и лишние аргументы инструмента по-прежнему отклоняются.

Подтверждения:

- `.venv/bin/python -m pytest -q tests/test_llm.py tests/test_llm_tools.py
  tests/test_schedule_agent.py tests/test_schedule_roundtrip.py
  --basetemp=.pytest-tmp-provider-index` — **63 passed**, 19,09 секунды.
- Ruff check, format --check, git diff --check — **PASS**.
- Независимое статическое ревью исправления — без замечаний.
- Выполнен отдельный сквозной запрос к реальной настроенной модели и настоящему
  MCP-серверу: «Какие занятия 16 ноября?», с фиксированным текущим временем
  15.11.2026, без истории и без Telegram. Два запроса модели успешно завершились,
  итог: **09:00–10:30 — Программирование, Учебная аудитория A**, дата 16.11.2026.
  Результат соответствует демонстрационному файлу расписания.

Таким образом, один реальный сценарий выбора и использования инструмента подтверждён.
Это не заменяет обязательный эксперимент на 12 запросах или проверку всех ошибок
живой модели. Работающий Telegram-процесс пользователя не перезапускался.
