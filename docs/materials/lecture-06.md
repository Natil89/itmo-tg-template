 Совет можно нарушить. Инвариант — никогда

 

 Конституция устанавливает руководящие принципы проекта, по которым оценивается каждый следующий шаг. Создаётся один раз, в самом начале.

 Источник: GitHub Spec Kit, Quickstart (перевод) — github.github.io/spec-kit/quickstart.html

 В Spec Kit живёт в .specify/memory/constitution.md ; каждая фаза работы над фичей оценивается против этого файла.

 

 
 AGENTS.md → как работать

 Конституция → что никогда

 

 

 3.1 

 

 

 Блок 3 · Конституция

 Инвариант проверяется по диффу за минуту

 Тест на инвариант: скажет ли машина или ревьюер однозначно — нарушен или нет.

 
 Инвариантов мало: пять строк важнее пятидесяти — каждый ещё защищать в CI и на ревью.

 
 Свойство Плохой вариант Хороший вариант 

 Короткий «Код должен быть чистым и поддерживаемым» «Тесты не ослабляем» 

 Без исключений «Обычно используем UTC» «Время внутри ядра — только UTC» 

 Проверяемый «Стараемся не ломать API» «Публичный API меняем только с версией» 

 

 3.2 

 

 

 Блок 3 · Конституция

 Каждый пункт — из реальной боли

 Пять пунктов, каждый закрывает класс историй, а не украшает документ.

 
 # Конституция сервиса уведомлений 1. Секреты — только из переменных окружения. Ни одного ключа в коде, тестах и логах. 2. Тесты не ослабляем: не удалять, не пропускать, не менять ожидание, чтобы «позеленело». 3. Публичный API `notify/` меняем только с повышением версии и записью в CHANGELOG. 4. Время внутри ядра — только UTC. Часовой пояс — при выводе. 5. Новые зависимости — только после обсуждения в issue. 

 п. 2 закрывает истории, когда агент «починил» тест, поменяв ожидание

 п. 4 решает, где живёт часовой пояс — выстрелит на слайде 52

 п. 5 — новая зависимость без обсуждения

 Блок 4 · Spec-driven development

 Спека — документ на вход, а не на выход

 Spec-driven development: определите, что и зачем делать, а затем превратите спецификацию в план, задачи и работающий код.

 Источник: GitHub Spec Kit (перевод) — github.com/github/spec-kit

 TDD перенёс фокус с кода на тест; spec-driven development переносит его с промпта на спецификацию.

 4.1 

 

 

 Блок 4 · Spec-driven development

 Чем левее стадия, тем дешевле ошибка

 Каждая стадия даёт на выходе markdown-файл в репозитории; между стадиями — утверждение человеком.

 
 Idea 

 

 Spec что и зачем 

 

 Plan как: стек, архитектура 

 

 Tasks что и в каком порядке 

 

 Implementation код 

 

 флажок — чекпоинт «утверждение человеком»

 
 Опечатка в спеке стоит минуту, ошибка в архитектуре — неделю.

 Человеческие чекпоинты ловят дорогие ошибки, пока они дешёвые.

 4.3 

 

 

 Блок 4 · Spec-driven development

 В спеке ни слова о коде — зато есть «не делать»

 Без раздела «не делать» агент делает всё сразу, а ревью растягивается на вечер.

 
 ## Фича: утренний дайджест **Зачем:** пользователи открывают приложение реже раза в неделю; дайджест мягко возвращает их без push-навязчивости. **Сценарий:** в 07:00 по часовому поясу пользователя приходит одно сообщение: прогноз на день и две рекомендации по одежде. **Не делать:** настройку времени рассылки, молчаливый режим, частоту «раз в час». Это отдельные фичи, в эту не входят. **Критерии приёмки:** - в 07:00 (Europe/Moscow) подписчик получает ровно одно сообщение; - нет прогноза — сообщение без блока погоды, а не тишина; - в логе одна запись на отправку, без дублей. 

 Ни слова о технологиях — стек в плане

 Критерии приёмки проверяемы: одно сообщение, а не два

 Через два блока эти критерии станут тестами

 Чинит — ломает — чинит то же самое

 1 · 2 · 3 · 4 · 5

 

 Третий круг по одной ошибке — сигнал остановиться.

 

 Симптом
 Тест падает, агент правит, падает другой, агент возвращает как было. Шаг 18 из 20, по кругу.

 Лимит шагов и бюджет · откат к чекпоинту и переформулировка задачи · крутится на месте — новая сессия и задача мельче.

 6.4 

 

 

 Блок 6 · Антипаттерны

 
 «Все тесты прошли» — а запусков не было

 1 · 2 · 3 · 4 · 5

 

 Не верьте слову — просите вывод команды; прочитать вывод быстрее, чем проверять самому.

 

 Симптом
 «Все тесты прошли», а в истории сессии ни одного запуска. Или тест «починен»: ожидаемое значение подогнано под код.

 Причина
 Модель оптимизирует «выглядит готово»; прогон тестов — отдельное действие, его можно пропустить или подправить критерий.

 Лечение
 Правило в конституции и AGENTS.md: перед словом «готово» — прогон · просить доказательства: какую команду запускал и что она вывела · ослабление теста — нарушение инварианта (п. 2, слайд 19).

 тест: прошёл или нет

 Блок 8 · Как читать diff

 Удалённое → зависимости → тесты → код

 Порядок неслучаен: удалённое и зависимости читаются быстро, а риск несут наибольший.

 

 1
 Удалённое. Что агент убрал?

 2
 Зависимости и конфиги. Что нового приехало?

 3
 Тесты. Усилены или ослаблены?

 4
 Код. Решает задачу? Не выходит ли за рамки?

 

 Ослабленный тест означает, что код можно не проверять — сразу отклонять.

 

 Вопросы агенту: почему так? что сломается? что запускал и что вышло?

 Блок 8 · Как читать diff

 Тест зелёный — дайджест приедет на полчаса позже

 Если бы читали только код и не заглянули в тесты — баг поехал бы в прод.

 

 п. 5
 Новая зависимость без обсуждения. pytz приехал сам; zoneinfo уже есть в стандартной библиотеке.

 —
 Ловушка pytz. Без значка, техническая: tzinfo=pytz.timezone(...) в конструкторе даёт смещение +02:30 вместо +03:00. Московский дайджест придёт в 07:30. Молча.

 п. 2
 Тест ослаблен. Проверка «равно 07:00+03:00» стала «в строке есть 07». Тест зелёный, сдвиг больше не ловится.

 

 Самый важный слайд лекции — здесь замыкаются конституция, спека и ревью.
