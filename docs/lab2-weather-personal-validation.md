# Погода и личное расписание: проверка

Дата: 16 ноября 2026. Python 3.12, PostgreSQL 16, MCP SDK 1.26.0; WSL.
Пользователь дополнительно к погоде выбрал личные расписания и добавление занятия
обычным сообщением с явным подтверждением. Правки выполнены в основном проекте
по ранее подтверждённому разрешению пользователя.

## Ответственности

- WeatherService читает только фиксированные Open-Meteo endpoints, проверяет геокодирование,
  единицы, IANA-зону, структуру и конечность погодных значений.
- PersonalScheduleStore владеет занятиями и переходами prepared → confirmed → executed,
  cancelled/expired. PostgreSQL обеспечивает блокировки и уникальность action_id.
- MCP-сервер выполняет чтение/подтверждённую запись; персональный режим не читает общий файл.
- MCP-клиент передаёт владельца и действие отдельно от аргументов модели в подписанном _meta.
- Агент проверяет предложения модели и готовит изменения; обработчик Telegram показывает
  кнопки, получает владельца из Telegram и вызывает запись только после подтверждения.

Отдельной БД на пользователя нет. Таблицы personal_schedule_actions и
personal_schedule_lessons находятся в существующей БД; каждая запись содержит владельца.
Инициализация повторяема и не удаляет старые данные. Новое личное расписание пустое.
Обезличенный JSON сохранён только для независимой демонстрации standalone-сервера.

## Исправление вопроса «погода в Питере»

Воспроизведена ошибка геокодирования без страны: API возвращает два места с именем
«Санкт-Петербург», у второго нет country, но присутствует country_code=MS.
Валидатор ошибочно считал весь ответ некорректным. Теперь при отсутствии перевода
используется двухбуквенный ASCII-код страны, а результат остаётся ambiguous.
Неверные/отсутствующие оба поля остаются ошибкой; первый город не выбирается.
Логирование содержит только этап HTTP/поиска/погоды, статус и тип ошибки, без
города, тела ответа, пользовательского текста или текста исключения.

## Точные названия и удобный режим выбора

По следующему пожеланию пользователя уточнён поиск: если API возвращает точный
Ереван и префиксные Еревани/Ереванлы, используются только точные совпадения.
Все настоящие одноимённые города остаются; если точного совпадения нет, похожие
варианты сохраняются. Население сортирует результаты, неизвестные значения не
дают приоритета.

WEATHER_LOCATION_POLICY=population — новый обычный режим бота. Единственный
положительный лидер по известному населению среди точных совпадений получает
погоду сразу. В ответе явно обозначены выбранное место и возможность уточнить
другое место. Неизвестное население других кандидатов допускается, поэтому выбор
явно является предположением, а не доказательством намерения пользователя.
Если все значения неизвестны/нулевые или лидеры равны, бот просит уточнение.

WEATHER_LOCATION_POLICY=strict сохраняет требование методички: одноимённые места
нужно различать явным выбором пользователя. Для сдачи и эксперимента следует
включить strict и перезапустить бот. Population — осознанное пользовательское
отступление от данного критерия, не утверждение соответствия всей лабораторной.
Самостоятельный MCP по умолчанию strict; основной бот передаёт свою настройку
через --weather-policy. Compose также передаёт пользовательское значение.

При успешной погоде финальные факты формируются из проверенного результата,
чтобы модель не могла заменить температуру и ветер новым ненужным вопросом.
Модель по-прежнему выбирает инструмент и получает его результат; обычные ответы
и действительно неоднозначные результаты остаются в модельном диалоге.
Если были также получены занятия, они сохраняются в итоговом выводе.
